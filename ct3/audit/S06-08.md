## Ranked findings

**1. `invalid_source` conflates policy with plumbing (line 36).** The three conditions
are: a non-string id (malformed provider output), an id absent from `records` (a genuine
integration bug), and a `restricted` record (a deliberate policy refusal). An operator
paged at 3am reads one code and cannot tell which. The fix is one branch and one code —
`restricted_source` for the policy case — and it matches the separation this audit has
already applied twice in `provider_safety.py` (`serialization_accounting_mismatch`,
`malformed_response_body`, `unsupported_provider`).

**2. Naive `record.timestamp` raises `TypeError` inside validation (line 52).** Nothing in
this range checks that `record.timestamp` is timezone-aware. `now` is always aware
(`datetime.now(timezone.utc)` or the injected clock), so the subtraction is safe only
because the model happens to store aware values. A single legacy row with a naive
timestamp turns every assessment that cites it into an unclassified 500. This is a
read-derived finding: one row with a naive timestamp settles it.

**3. `invalid_quote` conflates three provenance failures (line 40).** `len(quote.strip()) < 3`
is a length heuristic sitting inside a provenance check, and it is the same floor the
provider-side parser uses, so a quote of `"the"` satisfies both. The three causes should
not share a code: a non-string quote is malformed output, a too-short quote is a policy
floor, and a non-substring quote is a fabrication attempt. Only the third is the security
signal an auditor would page on.

## Also noted

- **`diverse` is dead (line 142).** It is computed from `departments_by_source` and never
  read after the signed-table rewrite; department diversity no longer enters the decision.
  Dead local, not an error-handling defect, but it is the kind of leftover that makes a
  reader believe diversity is scored.
- **`ProviderError` carries no message**, only a code and a fixed string. Fine for the
  API, insufficient for an operator without a log line beside it.
- **`AssessmentError` defaults to `code="invalid_assessment"`**; unreachable in this range
  because all four raises pass a code, but a future raise without one gets a code that
  names nothing.
- The `except (ValueError, TypeError)` around `Stance(...)` is the only catch in the range
  and is correctly narrow — `Stance(None)` raises `ValueError`, an unhashable value raises
  `TypeError`, and both mean the same thing to the caller.
