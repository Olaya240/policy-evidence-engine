## Findings

### F1 — the engine's own proposal guards are defence in depth, not a live path (Observed, via probe 1)

`engine.py:433-445` re-checks the shape of the provider's output and re-runs
`validate_assessment`. For a `MockProvider` — the only provider the runtime
constructs today — none of it can execute: `MandatoryProviderBoundary.assess`
validates and raises `ProviderSafetyError` first, and the `except
ProviderSafetyError` branch returns before line 433. Probe 1 makes this visible:
with the boundary's code collapse in place, the (c) and (d) cases report
`provider_failure`, i.e. they never reached the engine's own `malformed_output`
at line 434.

So the "validated twice" reading is wrong; it is validated once at the boundary and
once more only for a caller that somehow hands back an already-validated list.
That is fine as defence in depth, but a future reader who tests only through
`AssessmentEngine` will believe `engine.py:433-445` is covered when it is not.
Not changed here; the two layers agree today, and the tests assert the code, which
is the same under either layer.

### F2 — `invalid_source` cannot separate a withheld record from an invented id (Observed)

Both report `invalid_source`, with the same message, and the restricted record's id
and text are absent — so there is no existence oracle, which is the right trade,
but the code carries no signal that a *known* record was refused for `restricted`.
The reason (`eligible_provider_records`/`partition_provider_records` drops it) is
discarded at the boundary. Pinned as-is so a future split is visible; worker 5 found
the same collapse on the `challenge` path.

The boundary also refuses more than `MAX_PROPOSALS` proposals as `malformed_output`
(`provider_safety.py:959-962`), and the engine's own loop has no count cap — one
more refusal that exists only at the boundary and shares a code with shape errors.
Not pinned here (out of this clause's scope; it belongs to whoever owns the
amplification limit).

### F3 — the API erases the code that the engine preserves (Read, `app/main.py:28-30`)

`provider_error_handler` answers with a fixed sentence and
`status_code=503`, and does not surface `exc.code`. Every distinction this slice
pins — `provider_failure` vs `invalid_stance` vs `malformed_output` vs
`invalid_source` — is therefore available only to in-process callers; an HTTP
client sees one message. "The code is recorded" is true of the exception, not of
the response. Reported, not changed: the 503 body is a public contract owned
elsewhere.
