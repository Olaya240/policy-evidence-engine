## Ranked findings

### F1 — the trace can contradict itself about which record is representative (Read, 237-241 vs 313-317)

`_evidence_dispositions` rebuilds the group map from `decision.supports` and treats
`members[:-1]` as dependent. The same decision object already publishes
`dependent_support_ids`, and `_build_explanation_trace` emits it as
`source_group_analysis.dependent_support_record_ids`. Two implementations of the same
rule now sit in one trace payload, and they diverge the moment the order of
`decision.supports` is not the order that produced `dependent_support_ids` — for
example if the decision sorts its groups for deterministic output (it does sort
elsewhere: `dependencies=sorted(...)`, line 505).

Fail-closed today only because both derive from the same list in the same call. It is
a latent self-contradiction in an artifact a human auditor reads as evidence, which is
the worst place for one. Fix: compute `dependent_ids` from
`decision.dependent_support_ids` and delete the local group map.

### F2 — `zip` silently truncates the staleness policy (Read, 381-388)

`for item, evaluated_at in zip(evidence, evidence_evaluation_times)` has no length
guard. `challenge` (533-566) appends to `evidence_models` and to `evaluation_times`
in separate loops over different lists; a claim whose stored trace has fewer
`evidence_evaluation_times` than evidence rows — legacy claims, or any future edit that
adds an item without a time — loses the tail of the staleness table with no error. The
trace then under-reports which records were evaluated when, which is precisely the
audit question the table exists to answer.

A length assertion (or `itertools.zip_longest` with `None` fill and a
`PRIOR_GUARD_DECISION_UNAVAILABLE`-style basis) converts a silent omission into a
visible state.

### F3 — `_iso_utc` is host-dependent for naive input (Read, 221-223)

`value.astimezone(timezone.utc)` on a naive datetime interprets it in the host's local
timezone. Every caller in this range passes an aware value (`datetime.now(timezone.utc)`
or a normalised evaluation time), so this is latent — but slice 6 just normalised
`Record.timestamp` because the store can hand back offset-less text, and
`datetime.fromisoformat(previous["evaluated_at"]...)` at line 566 accepts a naive
string too. A single naive value in the chain makes the trace's `generated_at`
non-reproducible across machines, which is the property the injected clock was added
to guarantee.

### F4 — two definitions of "eligible record" (Read, 413 vs 466; the second is outside this range)

`_provider_assess` validates proposals against `eligible_provider_records(records)`
(line 413), while `_claim` builds its own index with `if not r.restricted` (line 466).
If the two ever differ, a proposal for a record the provider was allowed to see fails
as `invalid_source` even though the boundary approved it, or passes validation against
a record the provider never received. It is the same shape as the `unsupported_transport`
/ `request_too_large` code overloads slice 1 fixed: one predicate, two implementations,
one edit away from disagreeing.

Reported here because the contract belongs to `_provider_assess`; the call site is
`_claim`, which belongs to slice 8.

## Answers to the questions in the brief

**Can a disposition claim a status its evidence cannot support?** Not a verdict — the
codes are descriptive, and membership in `COUNTED_SUPPORT` / `COUNTED_CONTRADICTION` is
taken from the decision's own sets, so no item is labelled counted that the decision did
not count. It *can* contradict the trace's own dependency list, which is F1.

**Is `investigate` deterministic with an injected clock?** `investigate` (503-504) is a
list comprehension over `HYPOTHESES`, so ordering is fixed. The clock enters only through
`_claim`'s `now`, and every evaluation time is that same `now`. Determinism therefore
holds if the provider's output is deterministic — true for `MockProvider`, and not
guaranteed for a network adapter, which is the boundary's problem, not this function's.
One caveat: `generated_at` is `evaluation_times[-1] if evaluation_times else now` (line
491, outside this range), so the trace timestamp is a record's evaluation time rather
than the engine's clock; equal today, not by construction.

**Does it mutate the records it is given?** `investigate` does not mutate `Record`
objects. It does hand `Evidence` objects to `_review_item_with_trace`, which mutates
them in place (line 431-448: `review_state`, `proposed_stance`, `semantic_relation`,
`rationale`), and `challenge` depends on that by setting `evidence.disputed = True`
afterwards. Any caller that reuses an `Evidence` instance across two claims will see
the second claim's review overwrite the first.

**Zero records?** Inferred, not executed: `_provider_assess([])` returns the provider's
(empty) list, `evidence` is empty, `generated_at` falls back to `now`, and the decision
table is asked for a label on 0:0, which slice 6 read as `INSUFFICIENT`. No index into
`evidence` exists in this range, so nothing raises.
