## Findings, ranked

### 1. The dedupe key keeps `stance`, so one record read in both directions becomes two evidence rows and the claim reports a one-source contest as PARTIAL — `Read(508, 120, 183, 526)`

Lines. 508 builds the identity tuple; 509-513 append the surviving item. `stance` is in the tuple,
so `(OPS-101, "…", SUPPORTS, ACCEPTED)` and `(OPS-101, "…", CONTRADICTS, ACCEPTED)` are *not*
duplicates and both reach the claim. 120 then joins the two sides of
`supports`/`contradicts` by `source_record_id`, 526 builds
`dependencies = sorted({e.source_record_id for e in evidence})`, and 183 offers
"review both sources".

What the claim becomes. Both rows resolve to the same group id (`source_group or
source_record_id`), so each direction counts exactly one group — `independent_support == 1` and
`contradiction_groups == 1`; `decide` (`decision_table.py`
`_label`, `contest_blocks_decisive`) returns `PARTIAL`, `score 0.0`, `contested True`,
`STATUS.V2_DIRECTIONAL_EVIDENCE_BALANCED`. The stored claim then carries a `conflicts` string
reading "Fresh records point both ways: OPS-101 support and OPS-101 contradict."
(`Read(120)`), an `uncertainty` string telling the reviewer to compare "both sources"
(`Read(183)`) when there is one, and a `dependencies` list of length 1 (`Read(526)`).

Why it is not a scoring bug. Counting is per source group, so the double reading cannot inflate
or deflate the score, and `PARTIAL` is the honest label for conflicting readings of one record.
What is wrong is representational: the evidence can disagree with itself and with
`dependencies`, and the two human-readable strings convert one source into two. The remainder of
what the coordinator asked — *can stored evidence disagree with its `summary`?* — is **no**, and
that half is recorded under *Checked, no finding*.

Reachability. `MockProvider.assess` loops the eligible records and emits at most one proposal per
record per hypothesis, so the seeded path cannot produce the pair. `assessment_overrides`
(`test_engine.py:879-886` already drives one hypothesis through it, and `test_engine.py:347` does
so for another) and any real adapter can:
`_validate_provider_proposals` caps the array at `MAX_PROPOSALS` and validates each item, but
never rejects a repeated `(source_record_id, quote)` or an opposing stance on the same record
(`Read(provider_safety.py:950-975)`). So the mechanism is `Read`; *how often it occurs in
production* is `Inferred` and unmeasured.

The key's fourth member is also worth naming. `review_state` is review output, not proposal
data: with the guard on it is a pure function of `(quote, stance, hypothesis)` (`_review_item_with_trace`
447-492), and with the guard off it is `ACCEPTED` unconditionally (450-452). It is therefore
constant *within* one claim, so it changes no behaviour today — but it means the tuple cannot be
read as "the same proposal twice", and the next person to widen the guard (a second review state
reachable for one quote) silently changes what counts as a duplicate.

### 2. `investigate` pays five provider round trips and five whole-corpus serializations, and one failure discards the other four claims — `Read(496, 529-530, 998)`, cost `Inferred`

Lines. 529-530 is a list comprehension over `HYPOTHESES` (five ids, `models.py:33-37`), each
iteration calling `_claim`, which calls `_provider_assess` (496), which calls
`MandatoryProviderBoundary.assess` (997) → `serialize_provider_request(eligible, hypothesis_id)`
(998). The record context is identical on all five calls; only the hypothesis id changes. Then
`_claim` validates every returned proposal again at 505 (S08-02 F3 counts the second pass).

What it costs. Five provider calls, each with the eligible corpus re-serialized and re-sealed
(`provider_safety.py:249-256`, 128-record cap), plus ten validation passes over the proposals per
investigation instead of two. Call count is `Read`; the latency/money consequence is `Inferred`
and not measured — one investigation is five model requests where the interface needs one.

What it loses. The comprehension has no handler: a `ProviderError` at hypothesis *k* aborts
`investigate`, so claims 1..*k*-1 are discarded. Nothing is persisted yet (`main.py:122-125`
stores after the call), so the database is consistent — but `main.py:30` returns one body for
every code ("Assessment provider is unavailable or returned invalid output"), which names
neither the hypothesis nor the four that succeeded, and the only recovery is a full re-run of all
five. A transient failure on hypothesis 5 therefore costs ten provider calls, not one.

Timing. `now = self.clock()` sits inside `_claim` (503), after the provider call, so the five
claims of one investigation carry five different `generated_at` instants, and no field says they
belong to one evaluation. Each is individually correct; the investigation-level fact is missing.

### 3. The unknown-hypothesis refusal is correctly placed but wrongly classified, and the same bad id is a 503 on the other path — `Read(534-536, 18-21, 252-253, 426-428, main.py:23-30)`

Lines. 534-535 refuses before 536 calls `_claim`, so an unknown id never reaches
`_provider_assess`, the boundary, or the provider. Its `AssessmentError` is raised with no
`code`, so it carries the class default `invalid_assessment` (19) — the same code
`_validate_assessment_with_time` uses for a bad quote, source or stance. `main.py` registers
exactly two handlers, `store.DatabaseUnavailable` (23) and `ProviderError` (28); `AssessmentError`
is a `ValueError` with no handler, so if it ever escapes a route it is an uncontrolled 500 and
the code is lost on the way out.

The asymmetry. The same unknown id sent through `_claim` does not reach 534 at all: it fails at
251-253 (`ProviderSafetyError("invalid_context")`), which `_provider_assess` re-raises as
`ProviderError("invalid_context")` (426-428) and `main.py:30` turns into **503 "provider
unavailable"**. One entry point reports a caller mistake as an unhandled 500, the other reports
it as a provider outage; neither is a 4xx, and both discard the one fact the caller needs.

Reachability today: none from the API. `main.py:123` passes `hypothesis_id` only from
`INVESTIGATION_PRESET_HYPOTHESES[preset_id]`, a closed map, so 534 and 251 are both unreachable
over HTTP. The finding is latent-by-construction: `assess_hypothesis`'s public signature invites
a caller-supplied id, and the code that would then run is the two-way misclassification above.

Coverage, corrected after a truncated grep. The refusal **is** pinned to type and message
(`test_engine.py:865-867`, `pytest.raises(AssessmentError, match="Unknown hypothesis")`), and the
API rejects a client-supplied hypothesis id one layer earlier — `InvestigationCreate` is
`extra="forbid"` with no such field (`models.py:107-113`), pinned by `test_api.py:329-339`. What
no test pins is the `code` (nothing compares `AssessmentError.code` for this refusal anywhere in
the suite) and the `_claim`-path classification (`invalid_context` → 503), which is the half that
is wrong. My first pass searched only the first 20 matches and reported "no test pins it"; that
was a truncated read, and this paragraph replaces it.

## Checked, no finding

- **`generated_at` (503, 505, 514).** Every item is validated with the same `now`
  (`_validate_assessment_with_time`: `evaluated_at = now if now is not None else datetime.now(...)`),
  and `_claim` passes one `now` for the whole loop, so `evaluation_times` holds N copies of that
  one value and `evaluation_times[-1]` **is** `now`. The `else now` branch is therefore dead, and
  the field cannot currently differ from the claim's post-provider clock. No defect — but the
  name reads as "the last record's assessment instant", and the day a caller preserves per-item
  times (the way `challenge` carries them forward; not re-read here, outside my targets) that
  expression would silently stamp the trace's `decision_evaluated_at` with a record's historical
  time instead of the decision's. Worth a comment, not a change.
- **`summary` cannot disagree with the stored evidence.** 515 computes `status_decision` from
  `evidence` *after* dedupe, 523 interpolates only that status, and `_claim` never admits a
  disputed or pre-timestamped item (validated `Evidence` defaults `disputed=False`,
  `review_state=UNVERIFIED`; `stale` is derived from the record and the single `now`). So the
  summary is a pure function of exactly the rows stored beside it. The question's answer is a
  negative result, and finding 1 is the residue: the rows can disagree with each other and with
  `dependencies`, never with `summary`.
- **Alignment of the three parallel lists.** 511-513 append `evidence`, `semantic_decisions` and
  `evaluation_times` inside the same `if key not in seen`, so a dropped duplicate appends to
  none of them and index *i* still means the same row in all three; `_staleness_row` and the
  trace builders that zip them are safe here. (Contrast the positional rebuild in `challenge`,
  already recorded in the LEDGER slice-8 note.)
- **`version` default.** `_claim` hardcodes `version=1` (494) and `assess_hypothesis`/`investigate`
  never pass it, so every fresh claim is version 1; the increment belongs to `challenge`
  (outside my targets).

## Falsification and limits

- **F1 counter-observation:** the score does not move — group counting absorbs the double
  reading (`decision_table._count_groups`, `Read`). So the defect is confined to the two prose
  strings, `dependencies`, and the claim's readability, not to the verdict. I looked for a case
  where the same group is counted twice and found the guard at 167-170 doing exactly that
  subtraction for the disputed path; the undisputed path has the same property by construction,
  because `_count_groups` returns group *sets*.
- **F1 opposite-condition:** stance is a property of the *reading*, not of the record, so keeping
  both rows is intended and the real defect is only the wording/dependency collapse. Chased: 508
  keeps both, 120 renders them as two sources, 526 erases the direction, 183 says "both sources".
  That is the version I hold — F1 as written is the wording/dependency finding, not a scoring
  finding, and I have not claimed more.
