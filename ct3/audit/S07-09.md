## Findings, ranked by what a reader would get wrong

### F1 — The trace asserts a rule that no longer runs (line 327) — Read

```python
"department_diversity_uses_last_support_record_per_group": True,
```

Nothing computes department diversity for the verdict. `diverse` is computed at
line 130 and read by nothing; `departments_by_source`, built at 128-129, exists
only to feed it. The field is a hardcoded literal that still tells an auditor
(a) diversity is computed, (b) it uses the last support record per group, and
(c) the result matters. None of the three is true since the signed table took
group counts only.

Worse than dead code: the trace is the artifact a reviewer reads to explain a
verdict, so this is provenance for a computation that does not exist.

Correction: either delete the field, or replace it with the truth —
`"department_diversity": "NOT_USED_BY_DECISION"` — and delete `diverse` /
`departments_by_source` with it.

### F2 — `_iso_utc` is not UTC for a naive value (line 221-222) — Read

```python
def _iso_utc(value: datetime) -> str:
    return value.astimezone(timezone.utc).isoformat().replace("+00:00", "Z")
```

`datetime.astimezone` on a naive datetime interprets it as **system local time**
and returns the equivalent UTC instant. So for a naive input the function renames
a local clock reading as `...Z`, shifting it by the host offset without saying so.

Reachability: `evaluated_at` is normalised upstream now (line 50-51), so the live
route is a caller-supplied clock that returns a naive datetime — `generated_at`
(line 320) goes straight in. The trace then labels the result
`"timezone": "UTC"` and `"decision_evaluated_at"` in the same document.

Correction: normalise like the engine already does —
`if value.tzinfo is None: value = value.replace(tzinfo=timezone.utc)` — or refuse
a naive value explicitly. Silently reinterpreting it is the one option that keeps
the function name false.

### F3 — "final permission boundary" is the wrong function (line 399) — Read

```python
# This is the final permission boundary before any provider sees records.
permitted = eligible_provider_records(records)
indexed = {record.id: record for record in permitted}
```

`permitted` is used only to build `indexed`, the map that `validate_assessment`
checks a returned proposal against (lines 410-416). The provider sees
`records`, unfiltered:

```python
proposals = self.provider_boundary.assess(records, hypothesis_id)
```

The filtering happens inside `MandatoryProviderBoundary` (slice 5 verified the
projection there). A reader debugging "how did a restricted record reach the
provider" would land on this comment, look for the filter, find `permitted`, and
conclude the filter had run. The second half — that `permitted` decides which
records a proposal may *cite* — is the real contract and is unstated.

Correction: "Records are passed unmodified to the boundary, which enforces the
projection. `permitted` here only indexes the records a returned proposal is
allowed to cite, so a proposal citing a restricted or unknown id is refused."

### F4 — The disposition trail rebuilds the representative rule instead of using it (lines 227-232) — Read

```python
# Recover dependent items by matching their source-group membership and the
# exact representative rule used by the status branch.
support_groups: dict[str, list[Evidence]] = {}
for item in decision.supports:
    support_groups.setdefault(item.source_group or item.source_record_id, []).append(item)
dependent_ids = {id(item) for members in support_groups.values() for item in members[:-1]}
```

"the exact representative rule used by the status branch" is true only by
coincidence of iteration order. The status branch builds its own map and takes
`members[-1].source_record_id` as representative (line 137); this function
rebuilds the groups from `decision.supports` and assumes the same ordering, so
`members[:-1]` is the same set of dependents. No code is shared between them.

If `decision.supports` is ever sorted, or the status branch changes which member
is representative, the trace will name a different record as the dependent one
and nothing will fail. `_StatusDecision` already carries `dependent_support_ids`
(the field the trace reads at line 325) — this recomputation exists only because
the function did not accept it.

Correction: pass `decision.dependent_support_ids` in, and delete the rebuild.
Keep the comment only if it can say "same rule" without re-deriving it.

### F5 — "without changing any engine outputs" understates the failure mode (line 299) — Inferred

```python
"""Observe the shared status decision without changing any engine outputs.
```

The function is a pure observer of `decision`, but it also computes
`evidence_coverage(hypothesis_id, evidence)` (line 263) and the disposition list.
An unknown `hypothesis_id`, or an `Evidence`-shaped dict rather than an `Evidence`
(line 231 uses `item.source_group`, not `getattr`), raises here — and a raise is
an output change: the caller that used to get a claim now gets an exception.
Today every caller passes modelled evidence, so this is latent, not live.

Correction: state the two ways it can fail, or wrap the advisory block so a
coverage failure degrades to an absent field rather than a lost claim.

### F6 — `zip` without `strict` against a stated-per-record list (lines 304, 355) — Read

```python
evidence_evaluation_times: list[datetime | None],
...
for item, evaluated_at in zip(evidence, evidence_evaluation_times)
```

`zip` truncates to the shorter sequence. If a caller ever passes fewer times than
evidence rows, the trace silently reports fewer `evidence_evaluation_times` than
`evidence_dispositions` — in the block whose docstring promises every id is
recorded. The current callers build the two lists in one loop, so the lengths
match today.

Correction: `zip(..., strict=True)`.
