## Properties and the line that makes each one true or false

1. **P1 — `investigate` does not mutate the caller's records.** `_provider_assess`
   builds a new `indexed` dict (`:411`) and the boundary serialises records; nothing
   assigns to a `Record`. Compares `model_dump` before and after, so a mutation of a
   nested field is caught, not just rebinding.
2. **P2 — `challenge` does not mutate the claim it is given.** `challenge` starts
   `raw = current.copy()` and copies every evidence dict (`dict(item, disputed=True)`
   / `dict(item)`) — the aliasing fix recorded in the code comment. Shallow
   `current.copy()` is enough only because every nested list is rebuilt; a future
   edit that reuses `current["evidence"]` would break this property first.
3. **P3 — reproducibility under an injected clock.** `investigate` → `_claim` takes
   `now = self.clock()` once and threads it through validation, so two engines with
   the same clock produce equal bytes. The default clock (`:365`) is wall clock, so
   this property is false for default engines and the harness deliberately injects.
4. **P4 — a challenge preserves prior evidence and bumps the version once.** Every
   prior item is byte-equal except `disputed`, and `version=current["version"] + 1`.
   This is the structural half of "a challenge adds a review flag, never a rewrite".
5. **P5 — dispositions partition the evidence.** Same ids, same order, at least one
   code per item, every code in the vocabulary at `:391-399`, and
   `DEPENDENT_SOURCE_GROUP` implies `COUNTED_SUPPORT`.
6. **P6 — trace and claim agree.** `evidence_score`, `evidence_direction`,
   `STATUS.V2_*` rule id and a non-empty uncertainty string.
7. **P7 — a challenge to an already-counted group does not change the status.**
   This is the slice-6 double-count fix seen through the public API: the seed
   `CHECKLIST_UNAVAILABLE` claim is supported by `OPS-101` and contradicted by
   `OPS-102`/`OPS-110`, so marking `OPS-101` disputed must not move the label.

## Findings, ranked

1. **The disposition trail re-derives the dependent set with a different rule than
   the verdict.** `_evidence_dispositions` (`:237-240`) rebuilds support groups from
   `decision.supports` and calls every member except the last dependent
   (`members[:-1]`); `_summarize_status_decision` computes `dependent_support_ids`
   through its own loop. Equal today only because both take the last matching
   member; the trace is supposed to *observe* the decision, not recompute it. The
   two sets should be the same object. Read; the divergence needs one ordering
   change (a group whose members are not in input order) to become visible, and
   no test asserts the two sets are identical.
2. **`_iso_utc` silently assumes local time for a naive datetime** (`:223`). Slice 6
   now normalises record timestamps, but `generated_at` comes from `self.clock()`
   and an injected clock may be naive; the trace would then record a shifted
   timestamp with no error. Inferred from `astimezone` semantics.
3. **`department_diversity_uses_last_support_record_per_group: True` (`:330`) is a
   claim about a rule that no longer affects the verdict** — the signed table takes
   group counts only, and `diverse` is computed and unread in
   `_summarize_status_decision`. Trace provenance for a dead input is worse than
   either deleting the key or restoring the rule.

Lower severity: `_advisory_coverage_trace` runs `evidence_coverage` on every claim
even though the result is advisory-only and unused by the stored claim's top-level
fields (cost, not correctness); `semantic_guard=False` assigns
`item.review_state = ACCEPTED` in place, which is safe only because `_claim` owns
the freshly validated `Evidence`.

## What the harness does not cover

- No property constrains **counts**: `_summarize_status_decision` is slice 6's
  subject, and the harness only reads its output through the public claim.
- P7 passes vacuously if the phrase guard leaves `OPS-101` `UNVERIFIED` (then the
  status cannot change for any reason). That is the first result to check when the
  harness runs, and the counterexample print shows the before/after labels.
- Nothing here exercises the API layer, persistence, or a real provider.
