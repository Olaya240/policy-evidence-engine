## What slice 15 pins (`app/access.py`)

Deny path is the served path: `app/main.py:107` is
`return visible_records(store.list_records())` — no context, so `AccessContext()`
default applies. (`visible_records` occurs in `backend/` only at `app/main.py:8`
and `:107`.)

1. Default / `None` / explicit `AccessContext()` / `can_view_restricted=False` all
   return exactly the records whose `restricted` flag is false, in input order.
2. `can_view_restricted=True` returns every record, same objects, same positions
   (no duplication, no substitution).
3. The filter keys on the flag and nothing else: a visible record whose text is a
   restricted-looking canary passes; department, tags and `source_group` do not
   affect the outcome.
4. No mutation and no aliasing: input list and every record unchanged
   (`model_dump` before/after), returned list is never the input object, and
   appending to the result cannot reach the caller's list.
5. Empty input is safe under all three contexts; all-restricted input yields `[]`
   under deny and everything under allow; repeated calls are idempotent.
6. `AccessContext` is a frozen dataclass defaulting to deny (assignment raises
   `FrozenInstanceError`), and `Record.restricted` defaults to `False`, so a record
   built without the flag survives the deny path.

## Observation (not a defect, nothing left failing)

`execute`'s `estimated_budget_exceeded` branch is not reachable through the public
constructor: construction already rejects
`per_request * max_requests > ceiling`, `request_limit` is checked first, and the
signature is immutable, so `k * per_request <= max_requests * per_request <=
ceiling` for every reservable `k`. It is a defensive re-check against the shared
ledger. Pinned as observed behaviour: oversubscription is refused at construction,
and exhausting a legal run reports `request_limit` (with the reservation exactly at
the ceiling). Asserted as-is; not weakened and not reported as a bug.
