## Finding — the guard certifies the opposite stance and its decision follows

`_NEGATION_SUFFIX` (`semantic_guard.py:16-21`) matches a negation only as a
*suffix of the clause prefix*: `not|never|no|without` (+ `very|really|currently|yet|at all`)
then `[\s,]*$`, or an `n't` form. A negation separated from the cue by the verb
therefore never fires.

Observed (`python -c`, then pinned):

```
"There was not enough time to review every open item."
  -> relation SUPPORTS,    cue_ids ['TIME_PRESSURE.CONTRADICTS.enough_time_to_review_every_open_item',
                                    'TIME_PRESSURE.SUPPORTS.not_enough_time'], reason_code None
"We did not have enough time to review every open item."
  -> relation CONTRADICTS, cue_ids ['TIME_PRESSURE.CONTRADICTS.enough_time_to_review_every_open_item'], reason_code None
```

Two paraphrases of one proposition get opposite certified relations, and the
second has `reason_code is None` — a clean match, not an abstention. Under a
`SUPPORTS` proposal the guard then produces `review_state=UNVERIFIED`,
`reason_code=CUE_MISMATCHES_PROPOSAL`, `semantic_relation=CONTRADICTS`; under a
`CONTRADICTS` proposal the same sentence is `review_state=ACCEPTED`,
`reason_code=CUE_MATCHES_PROPOSAL`, and the claim's `evidence_score` is `-0.5`
(`status=CONTRADICTED`) while the supporting paraphrase scores `+0.5`
(`status=PARTIAL`) — Observed, `test_negation_gap_certifies_opposite_stances_for_the_same_proposition`.

So the answer to "an input where the guard's decision contradicts the stance it
reports" is this input, in the strict sense: the guard's decision is *ACCEPT* and
the stance it reports is the one the sentence denies. It is not a trace bug and
not an abstention — the wrong reading is promoted into the signed score.

Second, smaller instance of the same shape at the trace layer: an `ACCEPTED`
`SUPPORTS` row cites a cue id from the `CONTRADICTS` stance. `cue_ids` is appended
*before* the negation/contrast filters run (`semantic_guard.py:129-135`), so
rejected cues stay in the list with no per-cue rejection marker, and the row is
indistinguishable from a clean single-direction match — Observed,
`test_certified_row_cites_an_opposite_stance_cue_without_marking_it_rejected`.
The docstring ("which fixed cue strings matched or why they were excluded") claims
more than the payload carries: `reason_code is None` tells the reader that
exclusion did not happen for *any* cue in the list, which is false here.

Direction of a fix (not applied — this slice owns only the test file): allow the
auxiliary slot between negation and cue (`(?:do|does|did|have|has|had|was|were|
is|are)\s+not\s+(?:have\s+)?`) inside `_is_negated`, and record rejected cue ids
separately (`rejected_cue_ids`) so an accepted row's cited set is the set actually
used. Both are `Inferred` as fixes; only the defect behaviour above is Observed.
