## Findings, ranked by what they do to an operator at 3am

### 1. A short `evidence_evaluation_times` truncates the trace silently (line 370)

`zip` stops at the shorter list. The staleness section is supposed to carry one
row per evidence item; if the list is short — a persisted claim reloaded after
evidence was appended, or a caller that passes one timestamp for N items — the
trace reports *fewer* rows and nothing marks the gap. Worse, the row's own
`basis` field has a `PRESERVED_STORED_STALE_FLAG` branch for `None`
(373-375), so a truncated list and a fully preserved one produce the same shape.
A reader auditing why an item was counted sees no line for it and cannot tell
whether it was dropped or never existed.

*Inferred* from the language semantics of `zip`; the caller that could pass
unequal lengths is outside this range (I did not read `assess`/`challenge`).

Minimal fix: iterate `evidence` and look up the timestamp by index with an
explicit `None` when missing, or assert equal length and fail with a stated code.
The first is safer for persisted traces, the second for new ones.

### 2. `malformed_output` names two different failures (411 and 414)

411 is "the provider returned something that is not a list"; 414 is "an item's
key set is not exactly the four fields". One code, two causes — the same defect
class already fixed twice in `provider_safety.py` (`request_too_large` split from
an internal accounting fault; `unsupported_transport` renamed
`unsupported_provider`). An operator seeing `malformed_output` cannot tell a
vendor contract breach from a boundary projection bug.

Minimal fix: keep `malformed_output` for the list check, add
`malformed_proposal` (or `proposal_schema`) for the item check. Note the check
is key-set *equality*, so this code also fires for a benign extra field —
deliberate fail-closed per the slice-4 finding, but then the name should say
"schema", not "output".

### 3. `_iso_utc` reinterprets a naive datetime instead of refusing it (line 222)

`value.astimezone(timezone.utc)` on a naive datetime assumes the host's local
zone and shifts the value, then stamps `Z` on it. `generated_at` and
`decision_evaluated_at` are the two values a reader trusts to place a decision
in time, and a naive clock (injectable via `AssessmentEngine(clock=...)`, and
only normalised inside `_validate_assessment_with_time`, not here) yields a
trace that claims UTC while holding a shifted instant. No error is raised
anywhere, so this is invisible until two traces disagree by the host offset.

*Read* at 222; reachability is *Inferred* — it needs a caller that reaches
`_build_explanation_trace` with a naive value.

Minimal fix: `if value.tzinfo is None: value = value.replace(tzinfo=timezone.utc)`
before `astimezone`, matching the slice-6 fix in validation.

### 4. `except Exception` turns our own bug into a vendor fault (406-409)

The catch is justified — provider exceptions may carry prompts or record
content, and the comment says so — but it also covers `ProviderSafetyError`
subclasses already handled and plain programming errors raised *inside* the
boundary's own code (an `AttributeError` from a projection bug would arrive as
`provider_failure`). The audit has no evidence that this has fired; it is a
latent misattribution, not a live defect, and the alternative (re-raising
non-provider exceptions) risks leaking the very content the catch exists to
protect. Recorded, not recommended for change without a way to distinguish the
two safely.

### 5. `_advisory_coverage_trace` indexes coverage keys by subscript (271-296)

Nine bracket accesses into a dict produced by `evidence_coverage`. If that
module drops or renames a key, the engine raises `KeyError` — an unclassified
500 — instead of failing with a stated contract. Low severity because the two
modules ship together, but it is the only place in the range where a
cross-module schema is enforced by "it will raise if it changes".
