# T1 — a hanging provider holds the request open

Status this file supports: **proven for a real stalled loopback peer** (previous
row said "partially proven: timeouts configured; adversarial slow-server test not
run"). `THREAT-MODEL.md` is not edited here.

Evidence: `backend/tests/test_slow_provider_control.py` (new, 3 tests).

## What the test does

A real `http.server.ThreadingHTTPServer` on `127.0.0.1:0` accepts the POST, reads
the whole request body, and then sends nothing. Two stall shapes:

- `headers_only` — no response bytes at all; the client is waiting on the status
  line.
- `partial_body` — `200 OK` with `Content-Length: 64` and a 16-byte body prefix,
  then silence; the client is mid-stream.

The call goes through the unmodified production path:
`bounded_transport_call` → `BoundedTransportProvider._assess_async` → the real
`HttpxAsyncTransport.send` (real `httpx.AsyncHTTPTransport`, real socket, no
`MockTransport`, no patched `send`). Timeout `0.3 s` per call.

The server reports its own observations across threads, so "the socket was
released" is measured by the peer, not self-reported by the client:

- `request_seen` — the request body arrived, so the stall starts after dispatch.
- `peer_closed` — `recv()` on the accepted connection returned `b""`.

`parse_provider_proposals` is replaced with a recorder for the duration, so "no
partial body reached the parser" is an assertion about an interception that
would have fired, not about a code path nobody can reach.

## Assertions

1. `ProviderSafetyError` with `code == "timeout"`.
2. Wall clock `< 2.5 s` (≈8× the configured timeout).
3. `parse_provider_proposals` call list is empty.
4. The server observes EOF within 5 s of the failure.
5. Second test: `_TRANSPORT_SINGLE_FLIGHT` is unlocked before and after two hung
   calls, so one stalled peer does not wedge later calls.

## Measured

Per-call wall time, same code path as the test, 0.3 s timeout:

```
headers_only: code=timeout elapsed=304ms peer_closed=True
partial_body: code=timeout elapsed=303ms peer_closed=True
20s-timeout call still pending after 1.5s: True
```

The third line is the discriminator against "the server closed the connection on
its own, so the client returned early": with the same server and a 20 s timeout
the call is still pending after 1.5 s. The sub-second return is the timeout
firing, not the peer hanging up.

## Scope limits — what this does not prove

- **Rewired endpoint.** `HttpxAsyncTransport.__init__` enforces the pinned
  `https://provider.invalid` origin; the test replaces `_endpoint` afterwards
  (`object.__setattr__`) because the adversarial server is plaintext on loopback.
  Origin pinning and TLS are covered by `test_httpx_transport.py`, not here. A
  stalling TLS peer is not exercised.
- **Loopback, not the real network.** No packet loss, no middlebox, no DNS stall
  (the endpoint is an IP literal, so name resolution is out of the picture).
- **No slow-dribble case.** The two shapes are "nothing" and "prefix then
  nothing". A peer emitting one byte per interval is not tested; `_assess_async`
  wraps the whole exchange in `asyncio.wait_for(..., timeout=timeout_seconds)`
  (code read, `app/provider_safety.py`), which would bound total time, but that
  behaviour is not measured here.
- **Process-local guarantee.** `_TRANSPORT_SINGLE_FLIGHT` and the gate are
  in-process controls; nothing here speaks to a hung provider across workers.
