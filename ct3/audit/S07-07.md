## Ranked findings

### 1. A rejected record is reported as `UNCLASSIFIED_REVIEW_REQUIRED` — `Latent`, `Read(§_evidence_dispositions)`

The disposition ladder has no branch for `EvidenceReviewState.REJECTED`. A rejected
record is not support, contradiction, neutral, stale-accepted, unverified or disputed, so
`if not codes` fires and the trace tells an operator that the engine could not classify
it. That is a decision rendered by a human reviewer being reported as an engine gap, and
the disposition vocabulary already has eight precise codes while this one means "no rule
matched". Fix is one branch, `REJECTED_BY_REVIEW_EXCLUDED`, before the fallback.

Why it matters beyond cosmetics: the fallback code is the one a reader would use to spot
engine bugs. Filling it with ordinary review outcomes makes the signal useless.

### 2. `_iso_utc` reads a naive datetime as local time — `Latent`, `Read(_iso_utc)` + `Inferred`

`value.astimezone(timezone.utc)` on a naive value applies the host's local offset instead
of assuming UTC. `generated_at` comes from `self.clock()`, and `_validate_assessment_with_time`
now normalises its own timestamps, but a caller-injected clock may be naive and
`evidence_evaluation_times` is passed through untouched. The result is a trace whose
timestamps are shifted by the server's offset, silently, and differently on two hosts.

Slice 6 fixed the same class on the evidence side; `_iso_utc` is the remaining door.
The minimum fix is `if value.tzinfo is None: value = value.replace(tzinfo=timezone.utc)`.

### 3. `zip(evidence, evidence_evaluation_times)` truncates without a word — `Latent`, `Read(staleness_policy)`

If the caller passes a shorter `evidence_evaluation_times` list than `evidence`, `zip`
stops at the shorter one and the trace simply lists fewer records. No length check, no
error. A trace is the artifact a dispute is settled with, so a silently short list is
worse than a crash: it looks complete. One `assert`/`ValueError` on
`len(...) != len(evidence)` closes it.

### 4. `staleness_policy.decision_evaluated_at` is the trace's generation time, not the time staleness was computed — `Drift`, `Read(_build_explanation_trace)`

The block reports `decision_evaluated_at: _iso_utc(generated_at)` beside per-record
`basis: ASSESSMENT_VALIDATION`. Those are two different instants whenever the trace is
rebuilt from stored evidence: staleness was frozen at validation, while the field claims
the decision was evaluated when the trace was produced. The per-record rows are honest
(`evaluated_at` from the stored list); the summary line contradicts them. It should be
`None` or the maximum of the supplied evaluation times, never the wall clock.

### 5. `department_diversity_uses_last_support_record_per_group: True` advertises a rule that does not run — `Drift`, `Read(group_analysis)` + slice-6 finding

`diverse` and `departments_by_source` are computed and read by nothing since the signed
table took group counts only. The trace still asserts that department diversity is
derived from the last support record per group, which was true under v1 and is now
provenance for a computation that no longer feeds the verdict.

### 6. `_provider_assess` computes `permitted` and then hands the raw list to the boundary — `Drift`, `Read(_provider_assess)`

`eligible_provider_records(records)` builds `indexed`, then
`self.provider_boundary.assess(records, hypothesis_id)` is called with the **unfiltered**
list. Correctness therefore rests entirely on the boundary projecting internally (slice 5
pinned that it does), and this function copies/filters the record list for nothing. The
consequence a reader should know: a proposal citing a restricted record fails
`validate_assessment` as `invalid_source`, indistinguishable from a typo'd id, which is
the code-conflation class already recorded for this module.

### 7. `except Exception -> provider_failure` swallows our own defects — `Drift`, `Read(_provider_assess)`

The comment is right about not leaking prompts, and `ProviderSafetyError` is preserved
with its code. But the bare `except Exception` also converts an `AttributeError` in
`MandatoryProviderBoundary` into `provider_failure`, so a bug of ours presents as the
vendor's outage. Narrowing to transport exceptions plus a catch-all that reports
`internal_provider_boundary_fault` would keep the no-leak property and stop the
misattribution.
