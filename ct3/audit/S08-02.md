## Findings, ranked

### 1. Review overwrites the provider's rationale in place, so the claim keeps one fixed sentence per row and loses the proposal's reason — `Read(464-476, 479-487, 520-527)`

Lines. 464 copies `item.stance` into `item.proposed_stance`; 467 writes `semantic_relation`;
468-469 accepts; 470-473 and 474-476 write one of three fixed `rationale` strings onto the
object; 479-487 build the trace record from `proposed_stance`, `semantic_relation`,
`cue_ids`, `reason_code` — no rationale; 520-527 build the `Claim` from that same mutated
list and `model_dump` it.

Contract. 449 promises review "from that same decision" and the trace is versioned
(`phrase-guard-v1`) precisely so a reviewer can re-derive the call. 507's comment ("Never
promote a proposal or flip it to the opposite stance") shows the intent is that review sits
*beside* the proposal, not on top of it. 476's own sentence promises the proposal is
"retained in review annotations" — the stance is, the reason is not.

Attack it blocks. A provider, or a prompt-injected remote model behind `BasetenMuseSparkOpenAdapter`,
writing its own justification into text the engine then shows as engine reasoning. Overwriting
closes that for rows the guard accepts, which is why the overwrite exists.

Input that passes while violating intent. Two contradictory proposals for one hypothesis —
rationales "binder missing twice, see OPS-101" and "the desk was quiet, no checklist exists" —
both fail the cue match and are persisted with the identical 476 sentence. Nothing errors, the
trace is internally consistent, and the two rows are byte-identical apart from `quote` /
`source_record_id`. The reviewer asked to adjudicate those UNVERIFIED rows has no surviving
statement of what the provider claimed or why. Because `item` is mutated rather than copied,
`_review_item` (490-492) also hands the caller back a changed argument, and the same function is
the reviewer for a newly synthesized challenge candidate (563-564).

Why rank 1: live on every claim with the guard on, and it damages the artifact human review
depends on. It is invisible to the suite because both texts are non-empty strings; an
assertion would have to compare against the provider's original string, and none does.

### 2. `except Exception` reports a bug of ours as a failure of theirs, and nothing records which happened — `Read(425-445)`, trigger `Inferred`

Lines. 426-428 translate `ProviderSafetyError` correctly; 429-432 turn *any* other exception
into `provider_failure`; 443 translates `AssessmentError`; 444-445 turn any other exception in
our own validation into `malformed_output`.

Contract. 430-431 states the purpose: exception text may contain prompts or record content and
must not reach API errors or logs. `ProviderError.code` is the only structured outcome channel
(`evaluate.py:182,206`). `main.py:29` names the parameter `_exc` and 30 returns a single body for
every code, so the API client cannot tell the categories apart; the evaluation harness is the
only reader.

Attack blocked (sound). `MockProvider(failure_message=...)` raises `RuntimeError(message)` on
purpose, and `from None` on 432 drops the text. That half of the clause is correct.

Violation. The clause's scope is "anything raised during the boundary call", which includes the
engine-side half of it — eligibility filtering, request serialization, sealed-payload decode —
and 444's scope is "anything raised during our own validation". Neither is a provider fault and
both are reported as one. `except Exception` also contains `RecursionError` and `MemoryError`, so
exhaustion is reported as a provider verdict. `engine.py` has no logger (grep for `logging` over
`app/engine.py`: no matches), so a masked internal defect leaves no trace anywhere, and in the
harness it becomes a measured provider datapoint.

Input that passes while violating intent: **none found**, and that is the honest limit. I could
not construct an input from the three permitted providers (`provider_safety.py:985`) that makes
429 or 444 fire for a non-provider cause: the boundary translates its own faults (998-999 and the
adapters' own `except Exception → ProviderSafetyError`), and `MockProvider` raises only
`RuntimeError` on purpose. So this is a taxonomy defect with no demonstrated trigger. What would
settle it is an exception-injection test at 425 (stub boundary method raising `AttributeError`):
under "the catch-all fires" the result is `provider_failure` with no log; under "it cannot fire"
the exception escapes to the 500 handler.

`_validate_assessment_with_time` re-checks `restricted` (34) but knows nothing about

## Checked, no finding

- **Four-key allowlist (435-437).** It is not what stops a provider promoting its own review
  state: `_validate_assessment_with_time` reads exactly four keys (33, 37, 41, 44) and builds
  `Evidence` from an explicit keyword list with `review_state=UNVERIFIED` (64-67). So 436 is
  redundant for integrity, and its cost is brittleness — any additive adapter field (`confidence`,
  `cue`) fails the whole claim as `malformed_output` instead of being ignored. It constrains keys,
  not values: `rationale` has no length or content bound here (bounded in practice only by the 4 KB
  response cap), which is the enabling condition that makes finding 1's loss matter.
- **Guard-disabled branch (450-463).** Deliberate and recorded: 451-452 says so, 379-382 stamps
  `enabled: false` per claim, and it is a first-class evaluation mode (`evaluate.py:111,391`), not
  reachable from the API (`main.py:20` builds the default). Residue worth knowing: those rows get
  `semantic_relation: null` and `GUARD_DISABLED_BY_ENGINE_CONFIGURATION` while `review_state` is
  `ACCEPTED`, so `_summarize_status_decision` counts them exactly like reviewed support and the
  trace flag is the only marker. Fine as a baseline, wrong as a production mode.
- **Proposal count cap.** Absent at 433-445, present one layer down for every provider type:
  `_validate_provider_proposals` → `MAX_PROPOSALS = 128`, `provider_safety.py:959`. No engine-level
  gap.
