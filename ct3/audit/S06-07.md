# Slice 6 — performance audit, `engine.py:1-206`

Worker 7 of 10. Read-only; no source or test file touched.

**No measurement was taken.** There is no terminal in this session, so every figure
below is an *estimate* from the number of passes and the size of the inputs, not an

## 1. `_summarize_status_decision` iterates the evidence list 16 times

Counting the comprehensions and loops in the current body (lines 96-171):

| Pass | Source list | What it produces |
|---|---|---|
| 1 | `evidence` | `fresh` |
| 2 | `evidence` | `stale_accepted` |
| 3 | `evidence` | `disputed` |
| 4 | `evidence` | `unverified` |
| 5 | `fresh` | `accepted` |
| 6-8 | `accepted` | `supports`, `contradicts`, `neutrals` |
| 9-10 | `stale_accepted` | `stale_support`, `stale_contradictions` |
| 11 | `supports` | `independent_support` (set of group ids) |
| 12 | `supports` | `departments_by_source` |
| 13 | `supports` | `group_members` |
| 14 | `supports` | `dependent_support_ids` |
| 15 | `contradicts` | `contradiction_groups` |
| 16 | `disputed` | `disputed_fresh_accepted` |

Plus two more over the (usually empty) `disputed_fresh_accepted` subset.

At n = 10 a single list comprehension costs on the order of 0.4-0.8 microseconds in
CPython, so **est. 6-12 µs** of loop overhead, of which a single bucketing pass would
keep **est. 1-2 µs**. Net **est. 5-10 µs per claim**, and this is the largest single
item in the slice — larger than everything else below combined.

Worth changing: yes, but only as one pass that fills every bucket
(`fresh`, `accepted`, `supports`, `contradicts`, `neutrals`, `stale_*`, `disputed`,
`unverified`) from a single `for item in evidence:` with a small branch. That is a
mechanical rewrite with an obvious equivalence argument, and the slice-4 differential
harness already pins the outputs.

## 2. `diverse` is computed and never read

Lines 140-141:

```python
departments_by_source = {e.source_group or e.source_record_id: e for e in supports}
diverse = len({getattr(e, "department", None) for e in departments_by_source.values()}) > 1 if departments_by_source else False
```

`diverse` was the v1 input to the 0.78 confidence row. The signed table takes group
counts only, so nothing downstream reads it: it is not in `_StatusDecision`, not in
the trace builder's arguments, and not returned by `summarize_status`.

That is a dict construction (pass 12) plus a set comprehension over its values, for
**est. 1-2 µs per claim with zero effect**. This is dead work of exactly the kind the
audit is for: it survived the table rewrite because removing it was nobody's line.

Worth changing: yes — delete both lines. Cheap, safe, and it removes an
invitation to reintroduce a department-weighted score.

## 3. `summarize_status` pays for a trace it discards

`summarize_status` (line 201) calls `_summarize_status_decision` and keeps five of the
twenty fields. The discarded ones include `independent_groups` (a dict per group with
a member-id list), `dependent_support_ids`, and all eight evidence buckets.

Building those is **est. 3-5 µs** on a 10-item claim, paid on every call whose result
is thrown away. The expensive part is `independent_groups`: one dict plus one list
comprehension per group.

Worth changing: only if `summarize_status` is on a hot path. I could not check its
callers (search is rooted at a different repository here), so this is conditional —
if it is only used by tests, leave it; if the API uses it per claim, add a
`_summarize_status_decision(..., trace=False)` flag rather than a second function.

## 4. `dependent_support_objects` is a set built only to be scanned

Lines 157-158 build a set of `id()` for every non-representative member and then scan
`supports` again to collect the matching record ids. The group loop already visits
every member, so both the set and the scan are avoidable: append the id at the point
the group is built.

**est. 1-1.5 µs**, and it removes an `id()`-based check that is easy to get wrong
(the current version is correct, but it is the same construction that made the
aliasing bug in `challenge` hard to see).

## 5. `_StatusDecision` is a 20-field non-frozen dataclass

Construction is **est. 1-2 µs**; attribute reads in the trace builder add a little.
`__slots__` or a `NamedTuple` would cut it, but this is at the edge of the 1 µs bar
and it is the one change in this list that makes the code worse to read. Not worth
changing on this evidence.

## 6. Eager string joins

Four `', '.join(...)` calls build conflict text (lines 120-136). Each is inside an
`if` that is false for the common shape, so the cost is paid only when there is
something to say — and the text is stored in the claim, not discarded. Leave alone.

## What to change, in order

1. Delete `departments_by_source` and `diverse` (est. 1-2 µs, zero risk).
2. Fold `dependent_support_ids` into the group loop (est. 1-1.5 µs).
3. Single bucketing pass (est. 5-10 µs; needs the differential harness green).
4. `trace=False` for `summarize_status`, but only after checking its callers.

Items 1-3 together are **est. 7-13 µs** per claim, which would very likely erase the
+2.3 µs regression the coordinator measured for the whole decision path — that number
was a *delta* between two worktrees, so a saving of this size should show up clearly
in `ct3/bench.py` rather than being lost in noise.
