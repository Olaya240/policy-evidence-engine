## 1. Refusals — check, code, attack blocked

`AssessmentError.__init__(message, *, code="invalid_assessment")` is at `engine.py:20-21`.
**None of the three `challenge` refusals passes `code`**, so all three carry
`code="invalid_assessment"`.

| # | Check | Raises | Attack it blocks |
|---|---|---|---|
| 1 | `540-542` — `next((r for r in records if r.id == record_id and not r.restricted), None)`; `None` → `AssessmentError("Source record was not found")`, `code="invalid_assessment"` (default) | 422 via `main.py:162-163` | Challenging with a record id that does not exist, **or** that exists but is restricted (`CANARY`). Prevents a dispute from being attached to an inadmissible source. Merges two distinct conditions into one message. |
| 2 | `543-544` — `quote not in record.text or len(quote.strip()) < 3` → `AssessmentError("Challenge quote must be an exact source substring")`, `code="invalid_assessment"` (default) | 422 | A fabricated quote (not present in the source text at all), and a degenerate 1–2 character quote ("challenge every record with `a`"). The two causes share one message that is **false for the second**: a 2-character quote *is* an exact substring. |
| 3 | `556-559` — no evidence row matched, and `self._provider_assess([record], hypothesis_id)` returned no proposal for `record_id` whose `quote` contains the challenge quote → `AssessmentError("This source is not an assessed dependency for the selected claim")`, `code="invalid_assessment"` (default) | 422 | Attaching a challenge to a claim that never used the record — i.e. forging a dispute trail and inventing a dependency. **This is the only refusal that re-enters the provider** (`557`), and the only one whose check is a question to the provider rather than a membership test on the claim (see finding 1). |

Consequences for distinguishability (details in finding 3):

- `main.py:141-145` rejects a missing record as **404** and a non-substring quote as **422**
  *before* the engine is called, so refusals 1 and 2 are unreachable through HTTP except
  in one case: a **restricted** record passes the route's existence check and then hits
  refusal 1, surfacing as `422 "Source record was not found"` — the same prose the route
  uses for a 404 on a genuinely absent record, with a different status code.
- The route reads only `str(exc)` (`main.py:162-163`), so `exc.code` is never surfaced.
  `AssessmentError.code` has no consumer anywhere in `backend/app/` (the only `.code`
  reads are `evaluate.py:182,206,208`, on `ProviderError`).
- A validation failure *inside* the provider round-trip at `557` is not an
  `AssessmentError` at all: `_provider_assess` converts it to `ProviderError`
  (`engine.py:436-437,443`), which `main.py:28-30` maps to **503 "Assessment provider is
  unavailable or returned invalid output"**. So a bad provider proposal during a
  challenge is reported to the user as an outage, and the specific code
  (`invalid_quote`, `invalid_source`, …) is discarded by the handler.

## 2. Mutation and aliasing

**The input claim dict is not mutated.** Verified line by line:

- `547` `raw = current.copy()` — shallow, new top-level dict.
- `549` `raw["evidence"] = []` — rebinds the key **in the copy**; `current["evidence"]`
  (the caller's list) is untouched.
- `555` every appended row is a **fresh dict** (`dict(item, disputed=True)` or `dict(item)`),
  including the non-matching rows.
- `572-574` writes `item["review_state"]` only onto those fresh dicts.
- `626-633` writes only into `raw`.

So `main.py:159`'s `expected_claims=snapshot["claims"]` cannot be corrupted by this call,
and `store.apply_challenge`'s optimistic guard cannot raise a false `StaleRevision` from
this path. **The comment at `553-554` is accurate.**

**`dict(item, disputed=True)` aliases nothing nested.** `Evidence` (`models.py:65-78`) is
`str, datetime, str, Stance, EvidenceReviewState, Optional[Stance], Optional[Stance], str,
bool, str, Optional[str], bool` — every field is scalar/enum/datetime. There is no nested
mutable value to alias, and `574` only writes a top-level key. The shallow copy is sound
*for this schema*; it is not schema-enforced, so a persisted claim carrying an extra nested
key would be shared — but nothing in the function writes a nested value, so there is no
live mutation either way. `records` is read-only here (`540`, `557`), and
`_review_item_with_trace` at `563` mutates only the `Evidence` it just built at `560-562`.

**One real nested alias, at `589`:** `dict(prior)` shares `prior["cue_ids"]` — a list —
with `current["explanation_trace"]["semantic_guard"]["decisions"][i]["cue_ids"]`. The
returned claim's trace therefore holds the *same list object* as the caller's snapshot.
Nothing on this path mutates it, so it is latent rather than a live defect, and
`semantic_guard` returns a freshly sorted list per call (`app/semantic_guard.py`), so no
module-level list can leak. It is nonetheless the only place where the output aliases the
input, and the code copies `dict(prior)` in a way that suggests the opposite.

## 3. Findings, ranked

### F1 — The "not an assessed dependency" guard is a provider round-trip, so the refusal is replaced by an evidence append (High)

**Read(engine.py:556-565)** · **Inferred** for reachability.

The guard at `556-559` decides whether the claim *used* the record by asking the provider
whether the record *would* be assessed for the hypothesis (`557`), then filtering that
proposal list for `quote in a["quote"]`. When a candidate survives, `560-565` builds a
brand-new `Evidence` from `dict(candidates[0], quote=quote)` — the provider's stance and
rationale, the **challenge quote in place of the assessed quote** — marks it
`disputed = True`, and appends it. The claim's evidence list grows by one.

Everything downstream is then recomputed from that fabricated row: `576` status,
`626-629` score/conflicts/uncertainty, `632`
`dependencies = sorted({e.source_record_id for e in evidence_models})` — so **a challenge
can add a dependency the claim never had** — and `633` bumps `version`. This directly
contradicts the function's own contract at `545-546` ("it never rewrites its quote, stance,
source, or history"). Note the appending branch has neither the dedup key `_claim` uses
(`508-509`) nor a check that the candidate's assessed quote covers the challenge quote.

Reachability, honest: with `MockProvider` (`mock_provider.py:63`, `"quote": record.text`)
every evidence quote *is* the whole record, so `matching_evidence` at `551` is true for any
substring the route accepted and this branch is **unreachable** under the shipped default
(`main.py:20` `AssessmentEngine()`). It becomes live as soon as the active provider quotes
a *substring* — which is exactly what the Baseten adapter is instructed to do and what
`provider_activation.py:82` constructs — or when the stored claim's evidence quote is
narrower than the live provider's for the same record (record added to the store after the
claim was persisted). Because `main.py:153-156` challenges *every affected claim*, the
fabricated row can land on a claim the user did not select.

### F2 — A challenged stale record is simultaneously "do not count" and "count as stale context", and the decision table never sees the dispute (Medium)

**Read(engine.py:110-127)** · **Read(decision_table.py:160-161)** · **Read(engine.py:6 in
`_evidence_dispositions`)**.

`stale_support` / `stale_contradictions` (`engine.py:110-111`) filter on
`e.stale and review_state == ACCEPTED` with **no `not e.disputed` term**, while
`supports`/`contradicts` (`engine.py:103-104`) do exclude disputed rows, and `stale_accepted`
(`107-108`) reintroduces them. The first conflict line (`engine.py:114-115`) says the
challenged record "do not count … as uncontested evidence"; the stale-context line
(`engine.py:121-127`) simultaneously retains the same record as
`supporting: OPS-109`. Meanwhile `_count_groups` (`decision_table.py:160-161`) drops stale
rows *before* looking at `disputed`, so `disputed_groups` in the trace and
`status_rule_id` never register a challenge to a stale record, even though the evidence row
carries `disputed: true`.

**Two-challenge sequence that leaves the claim inconsistent with its evidence** — on the
`CHECKLIST_UNAVAILABLE` claim built from the seed records via the default engine
(`OPS-109` SUPPORTS 2025-01-03, therefore stale at 2026-11-01; `OPS-101` SUPPORTS fresh;
`OPS-102`, `OPS-110` CONTRADICT fresh):

1. `challenge(claim, records, "OPS-109", "printed checklist")` → the stale row is marked
   `disputed: true`, `conflicts` gains *"The user challenged evidence from OPS-109"*, and
   `conflicts` **simultaneously** keeps *"(supporting: OPS-109)"*. `disputed_groups = 0`,
   `status_rule_id` unchanged, because `_count_groups` skipped the stale row.
2. `challenge(<result>, records, "OPS-101", "loose note")` → `disputed_groups = 1`.

Final claim: **two** evidence rows with `disputed: true`, `conflicts` naming **two** record
ids, `disputed_groups == 1`, and `OPS-109`'s single disposition list
(`_evidence_dispositions`) carrying both `STALE_HISTORICAL_CONTEXT` and
`DISPUTED_REVIEW_REQUIRED`. No rule the trace states reconciles those numbers, and the
`+1` effective support the decision table still grants `OPS-101` is precisely what
`conflicts[0]` says must not be counted.

Related, same root: `551` matches on `quote in item["quote"]` — a *substring of the evidence
quote* — so a three-character fragment disputes whole rows, and neither `Evidence`
(`models.py:65-78`) nor the history event (`store.py:245`) records the challenged span. The
disputed passage is unrecoverable from the claim.

### F3 — The refusal taxonomy is unobservable, and one refusal can turn into a 503 (Medium-low)

**Read(engine.py:20-21, 543)** · **Read(engine.py:40)** · **Read(main.py:141-145, 162-163, 28-30)**.

All three refusals inherit `code="invalid_assessment"` (`20-21`), and the only caller reads
`str(exc)` (`main.py:162-163`), so a machine client must parse prose to tell "record not
found" from "quote not a substring" from "not an assessed dependency" — while
`raise ProviderError(exc.code)` at `engine.py:443` shows the code field *is* load-bearing on
the provider path, making the collision consequential rather than cosmetic.

Two further defects in the same check:

- `543` has **no `isinstance(quote, str)` guard**, unlike its sibling
  `_validate_assessment_with_time` (`engine.py:40`). Called directly on the engine (tests,
  harness, any non-FastAPI caller), `challenge(claim, records, "OPS-101", None)` raises
  `TypeError: 'in <string>' requires string as left operand` from `quote not in
  record.text`, not `AssessmentError` — an unhandled 500 rather than a 422.
- `len(quote.strip()) < 3` measures the stripped length while the substring test uses the
  raw string, so `"  ab  "` is refused with "must be an exact source substring" when it *is*
  one. `ChallengeCreate.quote` (`models.py:126`) admits `min_length=3`, so a
  whitespace-padded 2-character quote reaches the engine and gets a false reason.

## 4. Also observed, not ranked

- `541-542`: a restricted record and a nonexistent record produce the same message; only
  the HTTP status differs (404 from the route vs 422 from the engine).
- `589`: the `cue_ids` alias described in §2.
- `563`: re-running the semantic guard on the **challenge quote** (rather than the assessed
  quote) can set `review_state = UNVERIFIED` and overwrite the provider's rationale, so a
  fabricated row (F1) can carry a rationale that describes a quote it does not contain.
- `569-574`: the legacy `review_state` backfill is skipped entirely when
  `semantic_guard=False`, so the same stored claim yields different persisted JSON under
  the two configurations.
- `633`: `version=current["version"] + 1` is recomputed again from the DB row at
  `store.py:238`, so the value set here is dead.
