## Fixture

- Clock is frozen at `max(record.timestamp for record in SEED_RECORDS) + 1h`
  (2026-10-24T16:00:00Z). With a clock far from the seed records every item is
  stale and every decision is `INSUFFICIENT`/0.0, which makes property 2 vacuous;
  at this clock the decision table produces `PARTIAL` and `CONTRADICTED` with a
  non-zero signed score.
- Claims are produced by `assess_hypothesis(SEED_RECORDS, ...)` and JSON round
  tripped, i.e. exactly the shape a persisted claim is re-read as.
- Five scenarios reach the distinct branches of `challenge`:

| Scenario | Branch it reaches |
|---|---|
| existing item, full quote, `OPS-101` | `matching_evidence` by exact quote; `disputed` flips on an existing item |
| existing item, 32-char substring quotes, `OPS-109` | the same branch via the substring arm of `quote in item["quote"]` |
| `OPS-110` removed from the claim, then challenged | candidate/append branch: `_provider_assess` proposes it and the item is appended |
| the appended claim, challenged on `OPS-101` | append then match in sequence (two disputed items) |
| `TIME_PRESSURE` claim, `OPS-107` | a different hypothesis whose status is `CONTRADICTED` |

P3/P4 run a four-challenge chain on one claim (`OPS-101`, `OPS-102`, `OPS-103`,
`OPS-104`), re-feeding each result into the next call.

## Properties

| # | Property | Where the code decides it | Result |
|---|---|---|---|
| P1 | the dict passed in is unchanged after `challenge` (deep compare via `copy.deepcopy` snapshot plus a sorted-JSON byte compare of the same object before/after) | `raw = current.copy()`; every evidence item is re-created with `dict(item)` / `dict(item, disputed=True)`; the trailing `review_state` write lands on the copy | pass, n=5 |
| P2 | returned `status`, `confidence`, `evidence_score`, `uncertainty`, `conflicts` equal `_summarize_status_decision(...)` re-run over the returned evidence, validated back into `Evidence` | the last two statements of `challenge` | pass, n=5 |
| P3 | `version` increases by exactly 1 per challenge | `raw["version"] = current["version"] + 1` | pass, n=4 |
| P4 | evidence length never decreases | append-only candidate branch; the matching branch copies the item in place | pass, n=4 |
| P5 | count of `disputed` evidence == number of successful challenges that matched evidence, for distinct targets | `dict(item, disputed=True)` on match; candidate gets `disputed=True` | pass, n=4 |
| P5b | the same equality when one item is challenged twice | `disputed` is a boolean flag on the item | **FAIL**, n=2 |

## The property that fails

The brief states property 5 without a qualifier: the count of disputed evidence
equals the number of successful challenges that matched evidence. That holds for
distinct targets and is false as soon as two successful challenges land on the
same record.

```
same item challenged twice: 2 successful challenges matched evidence, but disputed evidence count is 1 (was 1 after one challenge); `disputed` is a boolean flag, so the count saturates
```

Minimal counterexample: base `CHECKLIST_UNAVAILABLE` claim, `OPS-101` challenged
twice with its own quote. Both calls succeed (version 1→2→3, evidence stays 7),
the second one flips no new item, so `disputed` count is 1 against 2 matched
challenges.

This is the literal statement failing, not the engine: the per-record contract
(`evidence length unchanged, one item per record, version still moves`, pinned as
`test_challenge_does_not_double_count_an_already_disputed_record`, worker 5's
suite) is what makes the flag idempotent, and an idempotent flag cannot equal a count of
attempts. The corrected property that does hold is the one P5 checks — the count
of disputed items equals the number of **distinct** records successfully
challenged, capped at one per record.

Reported as FAIL because the harness checks what was asked and exits non-zero;
do not "fix" it by changing the flag to a counter without a decision from whoever
owns the contract.

## Why these checks can fail at all

- P1's comparator is exercised: injecting `review_state = "UNVERIFIED"` into one
  evidence item makes it report `$.evidence[0].review_state: 'ACCEPTED' != 'UNVERIFIED'`,
  so the deep compare is not a tautology.
- P2 is not vacuous: the returned decision genuinely moves across scenarios —
  `PARTIAL/0.25/-0.25` → `PARTIAL/0.0/0.0` for the append case and
  `CONTRADICTED/0.5/-0.5` → `PARTIAL/0.5/-0.5` for `TIME_PRESSURE`. A returned
  claim that echoed the pre-challenge summary would fail the equality.
- P3/P4 are exact counters (`+1`, `len(after) >= len(before)`), not bounds.

## What the harness does not cover

- Refusals (unknown id, restricted record, non-substring quote, two-character
  quote) are out of scope here; worker 5's suite covers them.
- P1 compares values, not object identity: a nested dict could in principle be
  shared with the caller while still comparing equal. Only the returned evidence
  items' independence is pinned elsewhere (worker 5).
- `stale` is carried through `challenge`, not recomputed: a claim assessed at one
  clock and challenged at another keeps its old `stale` flags, so P2's "fresh
  summary" is fresh over the evidence's own flags, not over the current clock. I
  did not test a clock change mid-chain; nothing in the five properties turns on
  it.
- Not exercised: a claim whose evidence holds the same record twice, evidence
  from a hypothesis other than the claim's own, claims missing a `version` key,
  and records whose `source_group` collides with another record's id.
