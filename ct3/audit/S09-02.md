## The fields, in group counts

`s` and `c` are independent source **groups** (`_count_groups`, 143–177), not
records. Defaults: `POLICY_SIGNED_MARGIN` = (m=2, k=3, contest=False),
`POLICY_CONTEST_BLOCKS` = (m=2, k=3, contest=True), `POLICY_TWO_TO_ONE`
= (m=1, k=2, contest=False) — `decision_table.py:73-94`.

| field | where applied | meaning in groups |
|---|---|---|
| `min_support_groups` (m) | `_label:220` | `s >= m`. Only the SUPPORTED branch uses it; there is no contradiction-sided counterpart. `m=2` is what makes one support group never decisive. |
| `imbalance_per_group` (k) | `_label:220,222` | `s >= k*c + 1`, `c >= k*s + 1`. Default `k=3` needs `3c+1` support groups: **4** against 1 contradiction, 7 against 2, 10 against 3. For `k=3` this is exactly `score >= 1/2` (`ct3/THRESHOLD.md`, derivation re-checked by hand). |
| `contest_blocks_decisive` | `_label:218` | pre-empts both branches: any `s>0 and c>0` → PARTIAL, whatever the imbalance. |

Boundary map under the default (Observed, enumerated by calling `_label`):

```
c=0 -> s>=2   c=1 -> s>=4   c=2 -> s>=7   c=3 -> s>=10
s=0 -> c>=1   s=1 -> c>=4   s=2 -> c>=7   s=3 -> c>=10
```

## Three findings, ranked

### 1. The policy id names the multiplier, not the ratio; a ratifier signing "3_TO_1" gets 4:1 — Observed, and the alternative's own comment is wrong

`SIGNED_MARGIN_3_TO_1` (`decision_table.py:74`) with `k=3` applies
`s >= 3c + 1`, so one contradiction group needs **four** support groups:

```
_label(3,1, POLICY_SIGNED_MARGIN) -> PARTIAL
_label(4,1, POLICY_SIGNED_MARGIN) -> SUPPORTED
```

`ct3/THRESHOLD.md` knows the number in its title ("the 4:1 judgement") but then
labels that same grid "(a) current — 3:1" and quotes `s >= 3c + 1` underneath. So
two artifacts name the same rule by two different ratios; the code and the grid
agree, the label does not. A ratification decision that turns on "3:1 is strict
enough" is actually endorsing 4:1.

The same off-by-one makes the alternative's comment false. `POLICY_TWO_TO_ONE`
is documented at line 88 as "a two-to-one split settles a claim", but with
`k=2`: `_label(2,1) -> PARTIAL` and `_label(3,1) -> SUPPORTED` — which is what
`backend/tests/test_table_differential.py:247-248` asserts (2:1 is a tie under
this rule) and what `ct3/THRESHOLD.md` grid (c) draws. Code, test and brief agree
against the comment; the comment is the outlier, not the rounding detail.

The deeper shape of it: `k` is a multiplier in `s >= kc+1`, and only `k=3`
coincides with a score threshold (`1/2`). For `k=2` the integer rule happens to
equal `score >= 1/3`; for `k>=4` it does not, because the code's `+1` is not the
score-implied `(k-1)/2`. So "the multiplier" and "the score the label flips at"
are two different policy descriptions that agree only at the shipped value.

### 2. `ThresholdPolicy` accepts bounds that make both decisive branches true at once, and `_label` resolves the conflict silently in favour of SUPPORTED — Observed, latent

`ThresholdPolicy` (`decision_table.py:53-69`) is a bare frozen dataclass: no
`__post_init__` (`hasattr(ThresholdPolicy, "__post_init__") is False`), and the
`int` annotations are not runtime checks. Constructed values that are accepted
without complaint:

```python
ThresholdPolicy("F", min_support_groups=True, imbalance_per_group=1.5)   # ok
ThresholdPolicy("M", min_support_groups=-5, imbalance_per_group=3)       # ok
```

For integer `k >= 1` the two decisive branches are provably disjoint — adding
`s >= kc+1` and `c >= ks+1` gives `(k-1)(s+c) <= -2`, impossible for `s,c >= 0`
— which is why all three shipped policies are safe and why the Coq exclusivity
theorem is not in question. But the dataclass admits `k <= 0` and `0 < k < 1`,
where that argument fails and both labels are satisfiable on one shape:

```
k=0,   s=1, c=5 -> SUPPORTED     (1 >= 1 and 1 >= 0*5+1)
k=0.5, s=2, c=2 -> SUPPORTED     (2 >= 2 and 2 >= 0.5*2+1)   both branches true
k=-1,  s=1, c=1 -> SUPPORTED
```

No exception, no trace field, no log: `_label` simply tests SUPPORTED first
(line 220 before 222), so a policy whose bounds contradict each other reports
SUPPORTED for evidence that contradicts it 5-to-1. Today the exposure is latent
because the only constructions are the three module constants. It is a live
hazard for the module's stated purpose — the docstring at 55 calls the policy "a
named, ratifiable choice", and the manual tells a reviewer that switching is a
one-line change — since a reviewer who writes `imbalance_per_group=1` (reading it
as "1:1 is a tie") or `0` gets a rule with no exclusivity at all, and the module's
own warning ("must be re-proved") is the only guard. The cheap fix is a
`__post_init__` rejecting `min_support_groups < 1` and `imbalance_per_group < 1`,
which is exactly the region where the disjointness argument holds.

### 3. The floor on the CONTRADICTED side is missing and cannot be expressed; `min_support_groups` is one-sided by name and by use — Observed, design-level

`_label` applies `min_support_groups` only to SUPPORTED, so under the default:

```
s=1, c=0 -> PARTIAL        (blocked by m=2)
s=0, c=1 -> CONTRADICTED   (no floor on c)
```

"One source can never be decisive" therefore holds in the FOR direction only; a
single fresh contradiction group is decisive on its own. That may well be the
intent (a contradiction is a red flag), and `ct3/THRESHOLD.md` grid (a) shows it
(`s=0, c=1 -> C`) — but nothing in the policy surface records the intent, and
there is no `min_contradiction_groups` to set if a future reviewer wants the
symmetric rule. `POLICY_CONTEST_BLOCKS` is not that rule either: it only fires
when both sides are non-empty, so it still leaves `s=0, c=1` CONTRADICTED
(`test_table_differential.py:238`). A field named `min_support_groups` also reads
to a newcomer as "the minimum for any decisive label", which is the wrong model;
the class docstring says "SUPPORTED needs at least this many" and never says the
other side has none.

- `engine.py:177-186` calls `decide_table(...)` with the two counts and the three
  `disputed_*` arguments and **no `policy=`**, so `decide`'s default

  decide(s, c, policy=POLICY_SIGNED_MARGIN)` over the grid, and the id string), so
  repointing the default cannot pass silently.

  `confidence_rule_id` and `contested` (`engine.py:374-379`) but not `policy_id`,
  so a stored verdict does not say which threshold rule produced it. Answering
  "which policy was in force" requires reading source, not the artifact the audit
  system keeps.
