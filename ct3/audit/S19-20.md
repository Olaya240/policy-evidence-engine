## S19 — `backend/app/experiment_manifest.py`

### What it records

`ExperimentRunManifest.to_dict` (lines 163–186) builds an explicit literal dict, so the field set is closed:

`schema_version` (`"1"`), `run_id`, `dataset_sha256`, `code_revision`, `prompt_version`, `prompt_sha256`, `serializer_version`, `serializer_sha256`, `model_name`, `model_version`, `decoding{temperature, seed}`, `evaluator_version`, `attempts[]`.

Each attempt (lines 86–119) is exactly `case_id`, `request_count`, `latency_ms`, `input_tokens`, `output_tokens`, `error_category`. No prompt, response, proposal, rationale, quote or record-text field — and dataclass construction refuses unknown keywords, so a caller cannot widen it (`TypeError`, asserted). Module imports are only `hashlib, ipaddress, math, re, dataclasses, typing` (lines 4–9).

### Can it record a different experiment than the one that ran? Yes — at the class level, and the only in-repo producer does not identify the model at all.

Observed (tests):

- Every identity and digest is caller-supplied and echoed verbatim; nothing compares them against an executed artifact.
- A manifest with zero attempts is valid and serializes as a complete run record with `attempts: []`.
- `AttemptMetadata` accepts any safe `case_id` and any `request_count >= 1`; an attempt for a case that never ran serializes unchanged.
- `attempts` is a plain list attribute, so it can be replaced wholesale after construction and `to_dict` accepts the replacement (it only re-validates shape).

Read (the only producer, `backend/app/evaluate.py`):

- `run_id`, `dataset_sha256`, `prompt_sha256`, `serializer_sha256` are derived in-process from real artifacts: controller id, dataset bytes, `SYSTEM_INSTRUCTIONS`, `inspect.getsource(serialize_provider_request)` (lines 156–165).
- `code_revision=None` is passed literally (line 159) and `model_name`, `model_version`, `temperature`, `seed` are never set anywhere in the file (`grep` over `evaluate.py`). So the emitted manifest says nothing about which model produced the attempts — two runs on different models, or on different checkouts, serialize identically on those fields.
- `AttemptMetadata.request_count=run_controller.request_count` (lines 219, 232) is the cumulative run ledger counter, not the number of requests made for that case, so the field means something other than its name implies: case 3 of a run records `request_count=3`.

Verdict: the manifest is a faithful *allowlisted container* for whatever the caller asserts, not a record bound to an execution. It cannot presently distinguish the model or code revision that ran, and it will happily describe a run that did not occur, including one with no attempts at all.

### Does the file it writes live inside the repo? It writes no file.

Observed (AST test): no `open()` call anywhere in the module and no import of `os`, `pathlib`, `io`, `shutil`, `tempfile`, `subprocess`, `socket`. Read: `evaluate.py` has no `open(`, `write_text`, or `json.dump`; `main()` prints JSON to stdout (line 393). The manifest reaches disk only if the operator redirects stdout.

Related, report-only (outside this slice's module): the same metrics dict embeds `"dataset": str(DATASET_PATH)` (line 380) — an absolute local filesystem path to `backend/evaluation/gold_cases.json` (file present, 19,723 bytes) — into the output blob. Every data route returns **503 when the DB is uninitialized** (parametrized over all five). The `challenge` order of checks is record → quote → snapshot, so an unknown or restricted source record never reaches quote validation.

### Health

- Uninitialized DB → 200, `status: "ok"`, `database_initialized: false`, `database_available: false`, `authentication: false`, `human_review_required: true`. Body keys are exactly the seven read from lines 99–100.
- Initialized DB → 200, `ok`, both flags true.
- Corrupt file (`write_bytes(b"not a sqlite database at all")`) → 200, `degraded`, `available: false`. `PRAGMA schema_version` (line 96) is what makes corruption visible, as the comment claims.
- **Finding:** a configured path that `validate_database_path` rejects (`HACKATHON_DB_PATH` outside the data dir) yields `status: "ok"` with `database_initialized: false`, because the `ValueError` is folded into "not initialized" (lines 90–101). A deployment with a misconfigured path therefore advertises healthy while every data route 503s — the mismatch the endpoint exists to catch. Observed by test.

### Preset / question coupling

- `preset_id` present and question ≠ canonical → 422 with the exact detail `Question does not match the selected investigation preset.` Question is stripped before comparison (pydantic `non_blank`), so trailing whitespace is tolerated.
- Valid preset → 201, `question` equals the canonical string, exactly one claim whose `id` and `hypothesis_id` both equal `INVESTIGATION_PRESET_HYPOTHESES[preset]`, and `preset_id` in the response equals the requested value for all four presets.
- No preset → 201, `preset_id: null`, all five `HYPOTHESES` claims in order.
- Extra body field → 422 (`extra="forbid"`).

### `_derive_preset_id` refuses to guess

Lines 66–79 require a conjunction: exactly one claim, that claim a dict, `question` string-equal to the canonical question, and both `claim["id"]` and `claim["hypothesis_id"]` equal to the preset hypothesis. Fourteen non-exact shapes all return `None` (each a test case): no claims, two claims, wrong hypothesis, claim-id mismatch, hypothesis-id mismatch, question suffix, lowercased question, missing terminator, `question: None`, claims as dict, claims as string, claim not a dict, no `question` key, empty dict. A stored `preset_id` is never read: a foreign stored value still derives the canonical preset, and a matching stored value cannot rescue a non-canonical question.

### History ordering

`store.get_history` orders by `version` ascending (`backend/app/store.py:262`); after one challenge the route returns versions `[1, 2]` with events `["CREATED", "CHALLENGE"]` and `created_at` non-decreasing.

### Restricted record identifiers never appear in a response

Full flow — records, preset investigation, GET investigation, challenge, history, health — asserts no restricted `id` or restricted `text` appears in any body. Mechanisms, read: `store.list_records` drops `restricted` rows unless `include_restricted=True`; `store.get_record` adds `AND restricted=0`; `/api/records` applies `visible_records` again (default-deny). A challenge naming a restricted record returns 404 `Source record not found`, identical to a nonexistent id, so no existence oracle. Boundary: `store.list_records(include_restricted=True)` and `access.AccessContext(can_view_restricted=True)` exist and are reachable from in-process code — no route uses them today, and nothing in this slice's tests covers a future caller that forgets the filter.
