## Ranked findings

### A1 — HIGH: a future-dated record never expires

`engine.py:50` `age = (evaluated_at - record.timestamp).days`, `engine.py:53`
`stale=age > STALE_DAYS`.

A record timestamped in the future yields a negative age, so `stale` is `False` for
any amount of skew — a record dated 2099 is permanently "current proof". Three
variants matter:

- clock skew of a few minutes on an NTP-less host silently freezes freshness,
- a malicious or mis-entered timestamp buys permanent admissibility,
- `.days` truncates, so 90.9 days reads as 90 and is **not** stale; the boundary is
  a day wide on either side of the intended threshold.

Should: treat `age < 0` as stale (or reject the proposal as `invalid_timestamp`), and
compare `(evaluated_at - record.timestamp) > timedelta(days=STALE_DAYS)` rather than
integer days. Matters: freshness is the whole basis on which stale evidence is excluded
from the count, so this is the one input that can promote a record into the decisive set.

### A2 — HIGH: group identity is raw string equality, so look-alikes inflate independence

`engine.py:116`, `:119-120`, `:133` key groups by `e.source_group or e.source_record_id`
with no normalisation.

Two records whose group differs by a Cyrillic `о` in `Operations`, a zero-width space
copied from a chat client, or NFC vs NFD (`é` as one codepoint vs two) are counted as
**two independent sources**. That is the dangerous direction: the score and the
`SUPPORTED` threshold both rise on what is really one source. `dimensions` no,
`independent_support` yes.

Should: `unicodedata.normalize("NFC", group).strip()` and remove zero-width characters
before comparison, in one helper used by all three sites. Matters: independence is the
only thing separating "3 records" from "3 sources", and this is the only way to fake it
without lying about record ids.

### A3 — MEDIUM: a whitespace group name silently merges distinct sources

`engine.py:54` `source_group=record.source_group or record.id` treats `""` as absent but
`" "` as present; `engine.py:116` repeats the same idiom.

Two records with `source_group=" "` collapse into one independent unit, so genuine
corroboration is under-counted. The direction is conservative (it cannot manufacture
support), but the failure is invisible: the trace reports one group with two members and
nothing says the grouping came from a stray space.

Should: normalise, then treat empty-after-strip as absent. Matters less than A2 but it
is the same bug pointing the other way; fix both with one helper.

### A4 — MEDIUM: conflict strings are unbounded in the number of ids

`engine.py:102`, `:105`, `:107`, `:113-115` join **every** record id into the claim's
`conflicts` text, and `_evidence_dispositions` builds one entry per record.

Nothing in this function bounds the evidence list. At 10,000 items the claim carries a
multi-megabyte conflict sentence plus a 10,000-entry disposition array, all persisted and
returned over HTTP. Cost per call is linear and unremarkable (~10 passes over the list),
so this is an amplification problem, not a CPU one. Inference: I could not measure it.

Should: list the first N ids per category and append `and M more`. Matters: it is the
only unbounded output in a function whose input the provider can influence.

### A5 — MEDIUM-LOW: the empty department counts as a department

`engine.py:118` `diverse = len({getattr(e, "department", None) for e in ...}) > 1`.

A claim whose supporting records have departments `{"" , "Front Office"}` reports
`diverse=True`. Under the signed table diversity no longer moves the score, so this is a
trace-accuracy defect rather than a scoring one — but the trace is the audit artifact, and
it now asserts a diversity the data does not support.

Should: drop `""`/`None` from the set before counting, and say "unknown" explicitly.
Matters: a reader auditing why a claim was judged sees a diversity claim that is false.

### A6 — LOW: duplicate record ids are counted correctly but reported untidily

`engine.py:131-132` builds `dependent_support_ids` by excluding `members[:-1]` per group,
so independence is right even when the same record appears twice. Two cosmetic
consequences: the id is repeated in the conflict text, and
`representative_source_record_id = members[-1]` (`:124`) makes the representative depend
on input order, so the same evidence permuted names a different representative in the trace.

Should: de-duplicate by `source_record_id` before grouping. Matters: the disposition
array is supposed to be a stable contract; an order-dependent representative is a
second source of trace churn after the timestamps.

### A7 — POSITIVE (no action): stance outside the enum is handled

`engine.py:40-43` wraps `Stance(raw.get("stance"))` in `try/except (ValueError, TypeError)`
and raises `AssessmentError(code="invalid_stance")`. A dict, a list, `None` and an
unknown string all land on the same controlled code. This is the shape every other check
in the function should have, and two of them (A1, A5) do not.

## Cross-cutting note

Five of the seven items are the same failure mode this audit has now hit four times: a
predicate that is *nearly* right on the values someone typed and wrong on the values an
attacker or a broken client can produce — `""` vs `" "`, `é` vs `e+combining`, day
truncation, and an unbounded list. The cheapest structural fix is a single normalisation
helper plus a bound, both applied at the three grouping sites rather than per call site.
