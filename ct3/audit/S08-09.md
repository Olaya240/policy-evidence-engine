## 2. Findings, ranked by risk

### F1 — `main.py:152-158` challenges **every** affected claim in one comprehension. `[Read main.py:152-158; Observed]` — risk: medium

`store.get_challenge_snapshot` returns `affected = {claim_id} ∪ {cid : record_id in claim["dependencies"]}`
(`store.py:196-197`), and the route runs `engine.challenge` for each of them
(`main.py:152-156`) before a single `apply_challenge`. The target claim's evidence item
contains the challenge quote; a sibling cites the same record with a **narrower** quote,
so `engine.py:557` finds no match and the sibling takes the provider fallback
(`engine.py:558-564`). Two observed outcomes, both from `main.challenge(...)` driven
directly against a temporary seeded DB (probe script, record `OPS-110`, challenge quote
`"We had enough people on duty and the checklist binder"`; DB removed afterwards):

1. **Provider declines the sibling → the whole request 422s.** With the sibling's stored
   quote `"enough people on duty"` and a provider whose proposal for that record repeats
   the narrow quote, the comprehension raises `AssessmentError("This source is not an
   assessed dependency for the selected claim")`; `main.py:162-163` maps it to HTTP 422.
   Observed: `A result: HTTP 422 This source is not an assessed dependency for the
   selected claim`, and every claim in the investigation stayed at `version 1` — the
   target claim's legitimate challenge was discarded with it.
2. **Provider answers → the sibling's evidence set is widened, not just marked.** With
   the provider returning the wider quote for the sibling's hypothesis, the request
   succeeds, but `STAFFING_CONSTRAINTS` gains a **second** evidence row for `OPS-110`
   (`disputed=True`, the wider quote) and its `version` moves to 2. Observed:
   `B sibling rows: [('OPS-110', 'enough people on duty', False), ('OPS-110', 'We had
   enough people on duty', True)] version: 2`. Challenging claim X therefore rewrites
   claim Y's evidence set, and the history/`before` snapshot records it as a
   consequence of a challenge named at X.

Both outcomes are reachable through the route whenever a stored citation is narrower
than the challenge quote — which the route itself demonstrates in
`tests/test_api.py:569` + `:583` (`"binder"` stored, a longer quote challenged), where it
manifests as a 503 via the malformed second sequence. With the default `MockProvider`
this cannot happen, because its proposals quote the whole record text
(`mock_provider.py:63`), so every substring challenge matches directly.

Not chased: whether the deployed/adapter provider returns sub-record quotes (the adapter
tests use both `source.text` and a sentence quote, `tests/test_baseten_adapter.py:132`
vs `:204`); that is what decides whether F1 is live in a given deployment.

### F2 — `main.py:155` + `:157` pass the same `snapshot["claims"]` objects as input and as `expected_claims`. `[Read main.py:152-157, store.py:226; Observed]` — risk: low (contract currently holds)

The route relies on `challenge` not mutating the dicts it is given, because
`store.apply_challenge` compares the fresh DB read with `expected_claims` byte-for-byte
and raises `StaleRevision` → 409 (`store.py:226`, `main.py:162-163`) when they differ.
Aliasing is real (same objects, `store.py:196-197` returns references into
`_latest_claims`), but the engine copies at `engine.py:547-555`, and the successful
commits in the F1 probe prove `expected_claims` still matched the stored row after every
challenge ran. Regression coverage: `tests/test_engine_slice8_challenge.py:37-52`
(inputs untouched, no aliasing into the returned claim),
`tests/test_engine_slice7_contracts.py:68-74`, `tests/test_legacy_challenge.py:69-82`
(pre-upgrade claim whose evidence lacks `review_state` still commits — the permanent-409
scenario from memory is fixed and pinned).

### F3 — `evaluate.py:76-81` repeats F2 without a defensive copy, and has no 409 mapping. `[Read evaluate.py:76-81; Observed: `grep -n StaleRevision app/evaluate.py` → no matches]` — risk: low

Same pattern (`snapshot["claims"]` into `challenge`, then `expected_claims=snapshot["claims"]`).
A future aliasing regression would not fail one of the seven checks in
`deterministic_recomputation_history_consistency`; it would raise an uncaught
`store.StaleRevision` out of `_evaluate_recomputation_history` and take the whole
evaluation run down. Same for the double call at `evaluate.py:72-73`, whose equality
check is the only place that would *notice* input mutation — and only for the one
target claim.

### F4 — `evaluate.py:180` binds `claim` in the rejection branch and never reads it. `[Read evaluate.py:176-193]` — risk: info

For the four local-contract cases the only signal is whether `assess_hypothesis` raised
(`evaluate.py:178-185`); the returned claim, if the call unexpectedly succeeds, is never
read — the branch ends at `continue` (`evaluate.py:193`). Harmless (the case is then
recorded as `accepted`), but the binding invites reading the branch as if it inspected
the claim.

### F5 — `tests/test_legacy_challenge.py:115-118` cannot distinguish "external edit" from "challenge mutated my input". `[Read tests/test_legacy_challenge.py:106-118]` — risk: low (test-quality only)

The tampered claim is passed to `challenge` at `:115` and then used as `expected_claims`
at `:118`; either cause yields the expected `StaleRevision`. The mutation itself is
asserted independently at `tests/test_engine_slice7_contracts.py:74` and
`tests/test_engine_slice8_challenge.py:48-51`, so the coverage is not missing — this case
just does not carry its own weight. `tests/test_api.py:660-673` has the same shape (the
409 assertion would pass for either reason).

### F6 — `engine.py:498` `raw_items.extend(extra)` appends into the provider's returned list. `[Read engine.py:494-498]` — risk: info (latent)

`_provider_assess` returns the provider's own list (`engine.py:446`), and `MockProvider`
hands back a freshly `json.loads`ed fixture per call (`mock_provider.py:151-154`), so
today the extend touches nothing shared. But no caller passes `extra` (`engine.py:530`,
`engine.py:536` pass none), so the parameter is unused code whose only observable effect
would be mutating a provider-owned list. Not a live defect.

### F7 — Nothing asserts `records` survives `investigate` / `assess_hypothesis` / `challenge`. `[Observed grep; Read engine.py:420-423, provider_safety.py:167-177]` — risk: info

`evaluate.py:63` → `:66`/`:72` reuses one `records` list across four engine calls, and
`tests/test_engine.py:782-784` reuses `records` for `investigate` then `challenge`; both
would break if the engine ever started annotating records in place. Verified by reading
only (read-only projection, then a pure partition), not by a test.
